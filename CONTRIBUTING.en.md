# How to contribute

> **Translation.** This is a translation of the [Spanish original](CONTRIBUTING.md). If the two disagree, the Spanish text wins.

## Before you write code

1. **The specification rules.** A change in behaviour starts in [`spec/SPEC.md`](spec/SPEC.en.md)
   and in the vectors, and only then reaches the packages.
2. **Test first.** Every rule comes in with the vector or the test that proves it.
3. **Dependencies point inwards.** Read
   [decision 0001](docs/en/adr/0001-arquitectura-en-capas.md) before you add a module.
4. **A new design decision is a new file** in [`docs/adr/`](docs/adr/).

## Setting up the environment

You need Node 22 or later with pnpm, and Python 3.11 or later with [uv](https://docs.astral.sh/uv/).

```bash
pnpm install
cd python && uv sync
```

## What to run before opening a pull request

```bash
# At the root: vectors, style, types, architecture, tests and packaging for TypeScript.
pnpm check

# In python/: the same for Python.
uv run ruff format --check . ../tools ../examples
uv run ruff check . ../tools ../examples
uv run mypy
uv run lint-imports
uv run pytest
```

Continuous integration runs exactly this.

The stores that talk to a service are tested separately, against the real service:

```bash
docker run -d --rm --name omniwebhook-pg -e POSTGRES_PASSWORD=prueba -p 127.0.0.1:55432:5432 postgres:17-alpine
docker run -d --rm --name omniwebhook-redis -p 127.0.0.1:56379:6379 redis:8-alpine
docker run -d --rm --name omniwebhook-firestore -p 127.0.0.1:58080:8080 \
  gcr.io/google.com/cloudsdktool/google-cloud-cli:emulators \
  gcloud emulators firestore start --host-port=0.0.0.0:8080

export OMNIWEBHOOK_PG_URL=postgres://postgres:prueba@127.0.0.1:55432/postgres
export OMNIWEBHOOK_REDIS_URL=redis://127.0.0.1:56379
export OMNIWEBHOOK_FIRESTORE_EMULATOR=127.0.0.1:58080

pnpm test:integration                                # at the root: TypeScript
cd python && uv run pytest -m integration --no-cov   # Python
```

## Property-based tests

Whatever parses input from outside (headers, URLs, addresses, `retry-after`) also has tests that
generate random input and check that it never throws and that the result is always one of the
defined ones. They run with the rest of the tests. If one fails, it prints the minimal case that
triggers the failure: that case is added as a vector before the fix.

## Other runtimes

`pnpm test:runtime` builds the package and runs `ts/test/runtime/smoke.mjs`, a full cycle that
uses only web APIs. Continuous integration runs the same file on Deno and on Bun.

## Interoperability

`tools/interop.py` starts one agent per package and sends them the same requests: the vectors and
thousands of random variations. It checks that what one signs the other verifies, that both give
the same response to any request and, with `OMNIWEBHOOK_PG_URL`, that they share one and the same
reservations table.

```bash
pnpm test:interop                                   # builds TypeScript and runs the test
python3 tools/interop.py --seed 7 --rounds 400      # another seed, more variations
```

If a difference shows up, the correct response is first decided in the specification, the vector
is added, and only then are the packages fixed.

## Documentation examples

The code blocks in the READMEs and in the guides are checked with each language's type checker,
so that an example is not left using an API that has already changed:

```bash
pnpm check:docs
```

## Runnable examples

The receivers in [`examples/`](examples/) are tested too: the checker starts each one and sends
it a signed event, the same event again and one with a different secret.

```bash
pnpm check:examples
```

## Translations

Spanish is the original. There are translations of:

- **The README**, into English, Simplified Chinese and Brazilian Portuguese (`README.en.md`,
  `README.zh-CN.md`, `README.pt-BR.md`).
- **Everything else**, into English: the guides, the architecture decisions, the roadmap and the
  criteria in `docs/en/`, with the same file names as the originals; the specification in
  `spec/SPEC.en.md`; and this file, the security policy, the code of conduct and the READMEs of
  the packages and of the examples, with the `.en.md` suffix next to the original.

A change to an original has to reach its translations in the same pull request. You do not have
to remember: continuous integration fails if a translation no longer has the same headings, the
same table rows or the same code blocks as its original.

```bash
pnpm check:translations
```

Code blocks are copied as they are; in the guides only the comments are translated, and in the
specification not even those. The examples in the translations also go through `pnpm check:docs`.

## Conformance vectors

The files in `spec/vectors/` are generated by `tools/gen_vectors.py`; they are not edited by hand.

```bash
python3 tools/gen_vectors.py           # regenerates
python3 tools/gen_vectors.py --check   # verifies that the repo is in sync
```

The generator is a separate implementation of the specification and imports neither of the
packages. The secrets it uses are synthetic.

## Adding a signature scheme

1. Describe the format in the specification, citing the sender's public documentation.
2. Add its vectors to the generator, edge cases included.
3. Write the adapter in `adapters/schemes/` of each package. There is no need to touch the core.

## Commit messages

[Conventional Commits](https://www.conventionalcommits.org/en/) are used. The CHANGELOG and the
versions come from them.

## What does not go in the repository

- Real secrets, not even expired ones.
- URLs or data from real systems in tests, vectors or examples.
